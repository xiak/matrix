# Matrix 设计参考与待决定事项

## 适用边界

本页是外部研究形成的设计建议，不是新增需求、实现完成声明或已接受的安全契约。实际 IAM 规则由 [FEAT-006](../../../features/FEAT-006-platform-authorities.md) 拥有，控制台交互与 MOCK 能力由 [FEAT-007](../../../features/FEAT-007-control-plane-console.md) 拥有。发生差异时，以正式 FEAT 为准；建议被采纳后，应迁入相应正式归属，不在这里并行维护第二份契约。

腾讯可提供参考的是用户心智、授权概念和管理流程，不是 Matrix 必须兼容的产品目录、策略语言、标识符或 API。现有 Matrix 预览文档格式的决定已经属于 FEAT-007；本集合不将其改成腾讯格式，也不宣称支持腾讯策略直接导入。

## 优先借鉴的结构

最值得借鉴的是把“对象”“关系”“请求结果”分开：用户、组、角色、策略是可管理对象；组成员、策略关联、角色信任是关系；最终访问决定还需要具体操作、资源和请求上下文。只复制策略名称和关联列表，会遗漏用户真正需要理解的权限来源与影响。概念依据见 [身份关系](../concepts/identities.md) 与 [请求评估](../concepts/evaluation-and-abac.md)。

产品服务可以拥有自己的菜单和资源页面，但全局授权边界仍应由现有 IAM 契约承接。不要为每个概念分别建立服务、仓库、接口层或重复模型，也不要根据腾讯管理 API 的分组反推 Matrix 的领域拆分。

建议区分三个注册面：服务导航描述可发现入口；授权能力描述可授予的动作、资源类型与条件；运行时资源数据提供具体实例。导航隐藏不是授权，服务出现在产品目录也不意味着已具备任意资源级权限。

| 建议的能力描述 | 需要回答的问题 | 不能拿什么代替 |
| --- | --- | --- |
| 稳定动作标识及说明 | 这一授权实际允许哪个业务操作？ | 按钮中文名或当前 URL |
| 支持的资源类型与标识 | 能否限制到实例，哪些动作只能作用于全部资源？ | 任意可编辑的资源字符串 |
| 支持的条件与取值类型 | 哪些上下文可参与该动作的判定？ | 对所有服务开放同一套条件表单 |
| 动作分类与依赖 | 读、写、列表及关联操作如何解释？ | 单一“只读／管理”标签 |
| 可信属性来源 | 租户、主体、资源标签由谁提供和校验？ | 浏览器提交值直接成为鉴权事实 |

这不是要求立即新建一个通用注册平台。先在现有拥有者内表达已支持能力；只有实际服务扩展产生共同变化面时才抽取。腾讯授权粒度与条件的依据分别见 [策略与资源](../concepts/policies-and-resources.md)、[ABAC](../concepts/evaluation-and-abac.md)。

## 优先借鉴的 UX

策略详情应帮助使用者回答“授予了什么、对哪些资源、什么条件、谁在使用”，而不只是显示 JSON。关联选择器应保留直接授权与随组继承来源；撤销时说明移除的是哪条路径，以及是否仍有其他路径。具体交互分析归 [访问管理 UX](../ux/access-management.md)。

角色详情应区分信任与权限；身份提供商应与用户 SSO、角色 SSO 的入口和影响相连接，而不是归入泛化的密码安全页面。只有在真实接入得到验证时才能显示“联合登录成功”；模拟配置应保留明确的 MOCK 边界。

管理动作应区分“已提交”“处理中”“保存成功”和“生效已确认”。尤其是创建后再授权、删除服务相关角色、切换策略版本等流程，结果不能被压缩成一个通用成功提示。API 差异和传播依据见 [管理契约](../api/contracts.md)。

共享组件应优先覆盖复杂且重复的交互：可搜索选择器、带来源的关联列表、资源范围编辑、条件编辑、版本比较、页面内向导和结果反馈。宽高、密度、焦点、错误、骨架、深浅主题与多语言继续服从既有组件拥有者；不需要为腾讯每一张表创建一个独立组件体系。

## 不应照搬的部分

腾讯账号标识、QCS 格式、产品缩写和预设策略名称不是 Matrix 的领域语言。QCS 中保留但当前不能填写的 project 段，也不能成为恢复 Matrix 全局“项目”入口的理由。资源标识细节由 [策略与资源](../concepts/policies-and-resources.md) 解释。

腾讯产品配额、历史兼容行为、特定服务不支持资源限制的情况，以及 Deny 的特定例外，不应自动成为 Matrix 的目标设计。它们用于理解参考产品和识别风险，不是必须复制的缺陷。来源限制归 [证据边界](../evidence/caveats.md)。

同样不应复制云厂商全部计费、组织治理、密钥协议和安全产品，只因为它们出现在访问管理目录中。每项真实能力需要明确业务范围、威胁模型和可验证的服务端契约。

## 进入真实 IAM 前需要决定的事项

以下是需要在正式 FEAT 中回答的问题，不是本次研究新增的验收清单。

| 决策面 | 必须明确的语义 |
| --- | --- |
| 策略组合 | 支持哪些策略来源；显式拒绝、默认拒绝、边界与资源策略如何组合；不支持的语法怎样拒绝 |
| 列表授权 | 过滤发生在哪一层；总数、分页游标、排序、搜索和详情是否具有一致隔离语义 |
| 属性权限 | 谁可修改授权标签；缺失属性和未知值如何处理；谁可传递会话属性；怎样阻止借修改标签提升权限 |
| 委派与角色 | 谁可扮演角色、修改信任和传递角色；跨租户是否在范围内；怎样限制权限提升 |
| 策略生命周期 | 修订是否不可变、关联跟随默认还是固定版本、如何比较及回滚、如何处理并发编辑 |
| 传播与撤销 | 保存成功的保证是什么；会话、缓存和临时凭证何时受影响；是否能确认已经生效 |
| 管理用例 | 多步骤创建的事务边界、部分失败、超时未知状态、幂等和安全重试如何定义 |
| 联合身份恢复 | 更换提供商、签名密钥轮转、映射失败、退出及紧急恢复怎样避免锁死管理员 |

租户隔离不应依赖用户在 Header 中选中了什么。客户端选择是输入；可信租户和主体来源、跨租户拒绝规则仍由 IAM 的正式边界决定。不能因前端模拟了 ABAC，便把任意条件表达式或外部策略文档开放给真实后端。

## 最小可验证切片的建议

真正扩展时，建议从“某个租户内的一个用户，通过一个用户组的一条策略，对一个真实资源动作产生可解释结果”开始。把创建、关联、请求判定、拒绝、撤销和审计贯通后，再增加条件、角色与联合身份；避免先实现一整套无法被服务端验证的控制台入口。

围绕该切片优先验证以下行为：同一权限来自两个组时移除一个组不误报全部撤销；资源详情与列表使用一致范围；伪造租户、主体和资源标识不能越权；未知动作或不支持条件不会静默放宽；授权标签变化不会允许自我提权；信任不满足时不能扮演角色；创建成功但关联失败时能恢复而不重复创建。

这些测试建议只有被正式 FEAT 采纳后才成为实现门禁。本集合不充当验收证据，也不以 UI 可点击或 MOCK 模拟结果证明真实安全边界。
