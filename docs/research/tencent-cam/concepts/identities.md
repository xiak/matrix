# 身份与授权关系

## 主体、成员与授权是三种不同关系

腾讯云主账号拥有账户下资源；子用户是账户内部的授权身份。新建子用户或用户组并不会自然获得业务权限，创建某项资源也不会自动使子用户取得该资源所有权。需要“创建者可管理”时，应通过明确规则授予，而不是默认跳过鉴权。[^1]

| 对象 | 核心职责 | 不能误解为 |
| --- | --- | --- |
| 主账号 | 账户与资源所有者 | 日常普通管理员角色 |
| 子用户 | 可认证、可授权的主体 | 一组菜单权限 |
| 用户组 | 成员集合与团队权限分发 | 可登录、可扮演的身份 |
| 角色 | 在被扮演时使用的虚拟身份 | 用户资料中的职位字段 |
| 策略 | 定义授权规则 | 用户名列表或资源库存 |
| 身份提供商 | 外部认证与联合身份信任 | 密码规则或 MFA 设置 |
| 消息接收人 | 接收通知 | 可获得策略和 API 权限的子用户 |

腾讯另有协作者、企业微信子用户等类型。协作者涉及已有外部账户与当前账户的关联；消息接收人只承担通知职责。不能因为它们都出现在“用户”相关菜单或 API 分类，就将其合并成同一种授权主体。[^2]

## 账户级服务开通与用户授权

**官方事实**：腾讯云账户是资源和计量计费的主体，主账号是其所有者登录身份；子用户和协作者是在目标账户内被授权的身份。获得 `AdministratorAccess` 的管理员用户仍是子账号，不会变成资源所有者。[^12] **分析**：这里的“租户”应理解为隔离与归属边界，不能把“当前租户”“当前登录身份”“当前承担的角色”合并成一个管理员开关；其他云的组织、项目、订阅也不能仅按名称当成同一种账户作用域。

**官方事实**：COS 将注册账户、开通服务、创建授权身份、为身份设置权限、身份认证访问列为不同步骤。开通后，资源仍归主账号所有；子用户的资源权限和云服务代操作的服务角色需要分别授权。[^9]

| 上下文 | 对服务开通的含义 |
| --- | --- |
| 目标账户的主账号 | 已有账户所有者身份，不是开通后才成为管理员；具体产品仍可能有开通前置。 |
| 获得管理员权限的子用户 | 仍是子用户，能否开通由对应产品和被授予的操作决定，不能因“管理员”名称而视为主账号。 |
| 普通子用户 | 没有默认资源权限；已有某产品资源权限不自动证明具备开通权限。 |
| 协作者 | 在目标账户中是子身份；其自身账户的主账号身份不自动成为目标账户的所有者权限。[^2] |
| 角色或服务角色 | 角色承担及角色权限与开通不同；给服务代操作的角色授予权限，不等于给点击者授予权限。 |
| 多账号组织的管理账号 | 与成员账户不是同一个作用域；组织级开通必须按产品规定的管理账户上下文核对。[^10] |

**官方事实**：腾讯没有全产品统一的“只有主账号能开通”规则。OCR 允许已实名认证的主账号及获 `QcloudOCRFullAccess` 的子账号（子用户、协作者）开通，同一 APPID 下只需任一身份开通对应服务；调用量和资源包也按所属账户共享或归集。但文档对 2023-09-21 前已有该策略的子账号注明配置例外，不能只凭策略名称认定当前开通能力。[^13] 共享开通状态不等于所有未获授权的子用户都能调用接口，身份权限仍按 CAM 默认与实际授权判断。[^1]

集团身份管理允许管理账号或该管理账号下具有 `QcloudOrganizationFullAccess` 的 CAM 子用户开通；它要求已有多账号组织结构，不能外推为任意成员账户子用户均可开通。[^10] CloudBase Run 新版的初次开通角色授权则明确要求主账号完成，之后另外给子账号关联策略。[^11] 这是具体产品的前置约束，不是将所有服务角色创建都定义成主账号专属操作。

**分析**：开通状态属于产品规定的账户或组织范围；操作人、其当前身份、开通能力与资源操作能力是另外的维度。界面不应仅按账号类型、角色名、策略名或菜单是否可见推导可执行操作，也不能让每个子用户重复开通已经为目标账户开通的同一服务。开通资格与资源授权都须由对应公开契约确认。产品内部默认授权的例外见[证据限制](../evidence/caveats.md#契约与版本差异)。

**分析**：还要分别回答“能否查看服务目录”“能否为目标账户开通”“能否给其他身份关联策略”“能否让云服务代操作”和“能否使用具体资源”。其中任何一项获允许，都不足以替代其余决定。开通按钮应说明生效账户和缺失前置；已开通但无资源权限应提示联系管理员授权，而不是再次要求同意协议。读取开通记录无权限也不能被解释为账户一定未开通。

## 直接关联与随组继承

ListAttachedUserAllPolicies 明确区分直接关联与随组关联，并能返回来源组。一条策略可能沿直接关联、组 A、组 B 等多条路径到达同一用户。策略去重展示可以简化列表，但不能丢掉来源。[^3]

由此推导：解除直接关联后，来自用户组的授权可能仍存在；移出一个组，也不意味着来自其他组的相同权限消失。应从全部仍然适用的授权路径重新解释权限，而不是删除用户界面上的一行就宣布“权限已撤销”。

成员关系与策略关联的管理契约见 [API 契约](../api/contracts.md)。资源请求实际怎样决策见 [评估与 ABAC](evaluation-and-abac.md)。附加策略清单是决策输入，不是对任何资源的最终访问判定。

## 角色信任与角色权限

角色有两侧关系：信任策略描述谁可扮演、满足哪些条件；权限策略描述扮演后能操作哪些资源。角色不是用户组，用户也不是“加入角色后永久继承权限”。[^4]

普通 AssumeRole 流程同时要求调用身份具有相应扮演授权、目标角色将其配置为可信主体。获得角色临时凭证后，以角色身份访问资源。跨账户场景中，资源账户可以控制角色权限，来源账户则控制哪些主体能扮演该角色。[^5]

腾讯区分自定义角色、服务角色、服务相关角色等。服务相关角色的权限和生命周期由服务约束，关联资源可能阻止删除。不要把它们全部做成可随意编辑、删除的普通角色。[^4]

### 服务相关角色的具体例子

“支持角色的业务”页面具体列出的是服务相关角色：产品、角色名、角色类型、角色载体及说明链接，不是所有普通角色功能的兼容矩阵。角色载体表达可使用该角色的云服务，不是资源所属账户、用户组或目标资源范围。一个产品可以为不同场景提供多个角色。[^6]

批量计算的 BATCH_QCSLinkedRoleInAcrossService 由 acrossservice.batch.cloud.tencent.com 使用，其预设权限包含跨产品操作；示例还出现 finance:trade、kms:BindCloudResource 与 cvm:*。因此“给批量计算授权”不意味着只访问批量计算自身资源。应分别审阅可信服务与权限文档中的服务、动作、资源和风险，不应直接照搬宽权限预设。[^7]

CLS 的匿名分享场景另有 CLS_QCSRoleInAnonymousSharing，载体为 console-sharing.cls.cloud.tencent.com，策略列举日志查询、主题与仪表盘等动作。这说明授权应解释具体业务用途，而不是将所有云服务归成一个通用可信主体；本研究没有启用匿名分享或创建真实角色。[^8]

## 对 Matrix 的含义

这是公开契约的概念关系，不是腾讯数据库表结构。Matrix 的实际身份与权限实现由 [FEAT-006](../../../features/FEAT-006-platform-authorities.md) 拥有；控制台展示与 MOCK 边界由 [FEAT-007](../../../features/FEAT-007-control-plane-console.md) 拥有。设计参考见 [待决定事项](../matrix/design-reference.md)，不要据此直接新增领域层或重复身份模型。
