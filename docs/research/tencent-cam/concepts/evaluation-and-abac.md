# 请求评估、ABAC 与权限边界

## 模型判断

CAM 更适合描述为以策略为核心、同时支持角色化授权和属性条件授权的 IAM，而不是 RBAC 与 ABAC 二选一。用户组组织授权，角色提供可扮演身份；策略的资源、请求、身份／会话属性条件又能提供 ABAC 能力。这是对公开行为的结构性分析，不是声称腾讯使用了某一种内部引擎。[^1][^2]

## 一般授权链

一次可信的决策需要主体、当前账户或租户、动作、目标资源与所有者、相关属性、适用策略及其他限制。附加策略列表只能回答部分“权限从哪里来”，不能直接回答“这个请求一定成功”。用户组继承关系见 [身份关系](identities.md)。

一般身份授权遵循默认拒绝，匹配的 Allow 提供授权，匹配的显式 Deny 优先。权限边界限制用户／角色的最大范围，与其关联策略取交集；单独设置边界不授予权限。这个概括不能不加区分地覆盖资源策略、跨账户访问、组织管控和产品特殊行为。[^3][^4][^5]

资源策略或 ACL 是另一种授权入口，不能认为所有授权只来自 CAM 用户详情中的附加策略。尤其跨账户授权，要分别检查身份侧、资源所有者侧及具体产品契约；不能用一条没有适用范围的并集／交集公式代替完整决策。[^5]

## ABAC 的三个属性来源

资源标签描述已经存在的资源；请求标签描述操作所携带的标签；角色或会话属性描述当前身份上下文。腾讯通过标签授权和角色 ABAC 示例说明如何动态匹配资源或身份属性，新资源落入规则时不必逐个重绑策略。[^1][^2][^6]

策略自身的 Tags 元数据与策略条件中的资源标签不是同一种关系。前者用于管理策略对象，后者参与访问判断；CreatePolicy 将 Tags 与 PolicyDocument 分为独立输入。[^7]

**设计分析：**如果用户可以任意修改参与授权的标签，就可能通过改变属性取得原本不应有的访问权。标签创建、修改、移除和会话属性注入必须纳入授权设计；租户等可信属性应来自服务端认证上下文，而不是用户可自行填写的表单字段。此项是 Matrix 待设计的安全要求，不是对腾讯内部实现方式的描述。

## 条件的组合与缺失值

腾讯条件由键、运算符和值组成。条件块中的多个子条件需要共同满足；多值检查、for_any_value、for_all_value 与 if_exist 又有不同语义。特别是 if_exist 会改变上下文缺少某个键时的结果，不能当作普通的格式后缀忽略。[^8]

字符串、数字、时间、IP 等类型适配不同运算符；操作和列表接口对部分条件还有额外限制。因此，“JSON 语法正确”“条件类型正确”“目标服务支持”“与当前动作组合有效”是不同验证层级。[^9]

标签向导对不支持标签的接口，可以额外生成全资源授权。该行为会扩大权限边界；若 Matrix 提供相似辅助选项，应独立呈现具体操作及风险，不能自动添加来消除页面无权限提示。[^6]

## 资源列表不能仅靠前端过滤

腾讯文档分别描述有限资源列表授权和列表接口上的限制。能调用列表、能看到某行、能打开该行详情、能导出该资源敏感字段，是需要明确契约的不同问题。不能根据列表出现一行就推定全部详情操作均被授权。[^10][^11]

Matrix 的设计建议是由后端先确定可见范围，再计算过滤、总数和分页；详情、检索、导出和后台任务使用同样的授权边界。不应先向浏览器发送所有行和全量计数，再用前端隐藏。这个建议不代表当前代码已经具备该能力，正式状态仍由 FEAT 拥有。

## 腾讯特有例外

腾讯官方列出了资源列表查询混用资源／标签 Allow 与 Deny、COS 匿名主体与特定主体授权、部分计费权限组合等例外。其中，关联 AdministratorAccess 或 QCloudFinanceFullAccess 后，再拒绝特定 finance 操作可能不能达到预期。不能把它概括为“所有 Deny 无效”，也不能说腾讯所有服务中 Deny 永远无条件优先。[^11]

权限边界文档另明确注明暂不支持资源列表类接口。上述限制是理解参考平台的必要信息，并不是建议 Matrix 复制的行为。[^4]

限制的适用范围与未验证项集中在 [证据限制](../evidence/caveats.md)。密钥网络白名单属于另一个安全控制面，具体优先级见 [联合身份与凭证](federation-and-credentials.md)，不要与权限边界的交集规则混为一谈。
