# 访问管理 UX 机制

## 本文边界

本文分析外部交互背后的任务逻辑，不维护 Matrix 已实现页面清单。既有界面观察与正式交互合同、MOCK 限制、验收记录由 [FEAT-007](../../../features/FEAT-007-control-plane-console.md) 拥有。下面的建议不能作为功能已完成的证据。

## 从架构对象解释页面组织

以下是结合 IAM 工程师的[固定版本架构分析](https://github.com/xiak/matrix/blob/121e68373951a9261754661329a8e4e41bb6206c/doc/access-management/sources/tencent-cam-architecture-analysis.md)和控制台观察形成的 UX 分析，不是腾讯内部实现说明。对象定义仍由[身份关系](../concepts/identities.md)和[请求评估](../concepts/evaluation-and-abac.md)拥有。

| 用户正在回答的问题 | 页面承载方式 | 交互原因分析 |
| --- | --- | --- |
| 我正在管理哪个身份？ | 用户身份、访问方式与授权关系分区 | 能登录、持有密钥、拥有策略是独立维度；用一个“有权限”状态会掩盖它们。 |
| 这份权限从哪里来？ | 用户查看直接／组授权，组查看成员与策略，策略反查使用对象 | 同一关系需要从不同任务入口查到；撤销一条来源不等于撤销所有有效来源。 |
| 一份策略究竟允许什么？ | 列表定位，详情按服务汇总，再展开操作／资源／条件，另有 JSON | 列表承担寻找，摘要承担理解，JSON 承担精确检查；不能把完整计算塞进目录表格。 |
| 谁能使用角色，使用后能做什么？ | 角色载体／信任与权限策略分开，会话另有生命周期 | 信任不是权限授予，角色不是用户组，信任变更也不应被描述成既有会话全部撤销。 |
| 为什么本次访问被拒绝？ | 请求上下文与判定证据，而不是再次罗列关联策略 | 需要具体主体、操作、资源与上下文；策略检查、身份可用性和真实请求成功不能互相替代。 |

清爽的界面来自任务分层，而不是隐藏业务含义。默认展示当前对象和简短摘要；用户要检查来源、规则或影响时再展开。表格中的行链接应保留对象定位，修改关系前显示确切增减与影响，不能用一组没有上下文的“更多”动作代替解释。

### 所属产品不等于授权目标服务

2026-09-11 只读核对 [QcloudAccessForAgsCosReadWrite](https://console.cloud.tencent.com/cam/policy/detail/274481109&QcloudAccessForAgsCosReadWrite&2&All)：目录所属产品为 Agent Runtime，详情摘要列出对象存储 COS；展开后是 COS 的操作、资源与请求条件。结合[服务角色](../concepts/identities.md#服务相关角色的具体例子)，这说明产品的业务用途、可信服务主体和策略实际授权的目标服务是不同维度。

UX 推论：所属产品应取目录元数据，权限摘要应取策略文档与授权能力目录，不能互相推导；跨服务权限应清晰可见。描述文字与实际规则的冲突见[证据限制](../evidence/caveats.md#策略描述与实际规则)。

## 目录负责定位

策略目录负责寻找和进入策略，不负责在一屏解释全部授权计算。名称、产品、范围、类型与更新时间帮助定位；选择一条策略后，再在详情中查看文档、修订和关联对象。ListPolicies、GetPolicy、ListEntitiesForPolicy 的分离，也支持这些不同查询视角。[^1][^2][^3]

这比把所有 JSON、用户列表与版本管理塞进同一张 TABLE 更易理解。权限级别的真实含义见 [策略与资源](../concepts/policies-and-resources.md)，避免在界面中混用范围、操作类别和授权粒度。

2026-09-11 在已登录的[策略目录](https://console.cloud.tencent.com/cam/policy)核对：全部／预设视图的列为策略名、所属产品、权限级别、描述、上次修改时间、操作，带行选择框；自定义策略视图不显示所属产品和权限级别。全局策略（包括只读全局策略）的产品显示为横线，权限级别显示为全局权限。这是目录分类，不是操作的读写类别，也不是标签条件。

### 把参考体验翻译成 Matrix 契约

腾讯目录的视觉密度建立在它已有产品、权限级别、描述和关联动作等服务端元数据之上。Matrix 不能为了得到相同列数就在浏览器中从策略名称或 JSON 猜这些字段。当前固定契约只足以可靠呈现稳定策略 ID、显示名、管理方式、租户／平台作用域、状态、默认版本和更新时间；缺失平台元数据时，已有直接关联仍以稳定 ID 显示。

固定契约把策略目录限制为稳定排序、最多 256 项的完整管理快照，因此界面可做本地搜索、披露式筛选和分页，但不能显示虚构的后端总量、游标或“全选全部结果”。未来目录超过该边界时，应先由 IAM 增加正式分页、查询和选择范围合同，再改变 TABLE 行为。

用户页的当前实时合同也只证明直接、未撤销的 `USER` 策略关联。组继承、权限边界、角色会话和最终有效权限仍需各自证据。因此信息层级应保持：

1. 列表用于定位身份或策略，并标出对象类型、作用域与状态。
2. 详情区分身份信息、访问方式、安全凭证、直接关联和其他授权来源。
3. 关系变更明确目标、策略稳定 ID 与双方资源版本；目录刷新后版本变化必须重新选择。
4. 有效访问解释另起请求上下文视图，输入主体、操作、资源与条件，不能把“已关联策略”写成“本次请求允许”。

这也是为什么 Matrix 保留腾讯的任务拆分和渐进披露，却不逐列照搬：相同外观在不同证据基础上会产生误导。租户与平台策略目录分别请求；某一侧仅因 403 不可见时，另一侧仍可工作，其他错误则让实时场景明确失败，绝不自动换成 MOCK。

## 四种创建入口

同次只读核对，新建自定义策略提供：

- [按策略生成器创建](https://console.cloud.tencent.com/cam/policy/createV3)。
- [按策略语法创建](https://console.cloud.tencent.com/cam/policy/createV2)。
- [按标签授权](https://console.cloud.tencent.com/cam/policy/createByTag)。
- [按产品功能或项目权限创建](https://console.cloud.tencent.com/cam/policy/create)。

第四种页面显示“配置服务类型、开启权限、关联对象”步骤，当前可见候选是项目管理、主题模型和内容分发网络，并提示项目管理升级后使用标签授权、部分产品使用策略生成器。它是有历史背景的便利入口，不能据此推断所有产品都支持项目级授权。本次只打开页面观察，没有提交创建、关联或任何真实授权。

## 可视化策略生成器

腾讯生成器把策略编辑与名称、描述等提交信息分开，前者围绕效果、服务、操作、资源和条件组织，多条语句共同形成文档。JSON 与可视化是同一授权文档的不同表达，而不是两套独立权限模型。[^4]

对交互的分析：先选服务与操作，再决定资源输入能力，可以减少无效组合；条件适合按需展开。切换服务或操作若使原资源、条件不再合法，应提示受影响项，而不是静默删除。切换 JSON 与可视化模式时，不能解析的合法扩展语法应保留在 JSON 中，不能在用户不知情时丢失。

标签创建的辅助授权也需要独立解释。对不支持标签的操作补全全部资源权限，是权限扩张，不能伪装成普通“补全体验”开关。[^5]

## 校验不是一个红色错误框

腾讯策略分析器区分错误、警告与建议，涉及结构、元素、资源格式、条件类型、冗余和长度等。它说明成熟策略编辑器的验证应超过 JSON.parse，但静态检查仍不证明任何具体主体的请求一定被允许。[^6]

建议将阻断提交的错误定位到具体语句和字段；宽泛通配与高权限作为可理解的风险提示；冗余项作为建议。没有语法错误不应显示“权限已验证通过”，因为授权来源、边界、会话及产品支持还未必纳入评估。

## 授权选择、审阅与撤销

权限选择器应同时回答选择了什么、授予谁、作用范围多大。用户组继承来源不应被用户详情上的直接解绑按钮掩盖；策略变更还应能反查使用对象。[^3][^7]

### 创建用户中的候选策略表格

在快速创建用户页的策略选择弹层中，左侧是带类型筛选和关键词搜索的候选表格，右侧是独立滚动的已选清单。表格包含名称／描述、类型、权限级别、标签及引用计数；右侧显示单次最多选择 30 项。这个 30 项提示是该交互的批量上限，不能外推为用户最终只能关联 30 条策略。

当前观察样本显示 1,022 个候选项，但初始仅加载 10 行。点击表头复选框后右侧变为 10/30；继续滚动使候选行增至 20，已选仍是 10/30，新加载的行没有自动被选中。因此本次观察支持“全选针对当前已加载候选”，不支持“搜索结果全部授权”，也没有证明腾讯采用固定分页。选中 AdministratorAccess 时，弹层还提示广泛权限与重复授权风险。观察后取消弹层，原用户草稿仍显示未授予权限，没有提交创建或应用权限。来源和观察日期见[来源记录](../evidence/reading-map.md)。

可借鉴的机制是：候选数量、当前选择范围和已选总数必须彼此区分；加载更多不能悄悄扩大授权。采用分页还是增量加载，是实现方需要明确的独立决定。

“是否确认”本身提供的信息很少。更有价值的审阅内容是主体、目标资源、直接／继承来源、是否包含全局或权限管理能力，以及此次操作会改变哪些关联。复制权限时还要明确复制的是直接策略还是组成员关系，不能含糊地表示复制整个用户。

## 历史版本与生效

只查看旧版本不能改变当前生效版本。回滚前应展示版本差异和关联影响；删除版本与删除策略是不同任务。控制台版本指南与 UpdatePolicy 的公开行为存在差异，详见 [API 契约](../api/contracts.md)，不能仅根据按钮名称推测后端命令。[^8][^9]

## 响应与安全状态

Matrix 的体验建议是点击后立即给出页面、弹层或局部反馈，再加载数据；不应等请求返回才展开，也不应在导航后长时间保留旧内容作为新目标的假象。选择列表、影响查询和 JSON 分析应拥有自己的加载、错误和重试边界，避免整页因为局部请求一起重渲染。

快速反馈不等于乐观宣称权限已变更。最终一致性和任务型删除说明“提交成功”“处理完成”“权限已传播”可能不同；后端无生效确认能力时，UI 应诚实说明。[^10][^11]

窄屏可以减少并排列和步骤说明，但不能丢失当前步骤、目标身份、已选摘要和错误定位。具体组件尺寸、主题、键盘和动效合同应继续归 Matrix 的公共组件与 FEAT，而不是写入腾讯参考知识。
